# Протокол Bulk Epin

Реализация сверена с [официальным OpenAPI 1.0.0](https://bulkepin.com/api/public/v1/openapi.json) и [Reseller API](https://bulkepin.com/reseller-api) 8 ноября 2026 года. Проверялся также загрузчик FunPay Cardinal на коммите `c09dd13be25072bb3d5cdbba33d1e0d70e477710`.

Базовый URL: `https://bulkepin.com/api/public/v1`. Авторизация: заголовок `Authorization: Bearer <key>`. Перенаправления HTTP запрещены, чтобы не передавать ключ на другой адрес. Таймаут подключения 10 секунд, чтения 40 секунд. Автоматических повторов запросов покупки нет.

| Метод | Использование |
|---|---|
| `GET /ping` | Проверить ключ. |
| `GET /balance` | Баланс в USD. |
| `GET /catalog` | Доступные виды товаров. |
| `GET /products` | Поиск и пагинация каталога. |
| `GET /offers` | Номиналы, регионы, ID предложения и поля получателя. |
| `POST /quote` | Проверка получателя, количества, предварительной цены и баланса. |
| `POST /orders` | Создание или восстановление покупки с сохранённым `idempotency_key`. |
| `GET /orders/{id}` | Опрос по локальному ID заказа Bulk Epin, не по `provider_order_id`. |

Запросы выполняются последовательно с интервалом минимум 1,1 секунды. HTTP 429 включает общую паузу с учётом `Retry-After` и `retry_after_seconds`. Каждый заказ проверяется не чаще раза в 10 секунд; при очереди время ожидания увеличивается. После 30 минут обработки интервал для такого заказа увеличивается до 60 секунд.

Ключевые свойства:

- `/quote` ничего не покупает и не резервирует. Публичный `POST /orders` не принимает ограничение цены.
- До POST записываются точное тело, случайный ключ операции и отпечаток API-ключа. Повтор события FunPay не создаёт новую строку журнала.
- Идемпотентность поставщика привязана к аккаунту. Одинаковый ключ возвращает прежнюю покупку, даже если тело различается. Поэтому при восстановлении тело не пересобирается.
- HTTP 200/201 не подтверждает выдачу: используются `id`, статус и последующий GET. Сверяются тип товара, родительский продукт и количество.
- При сетевой ошибке создания результат неизвестен. Автоматический повтор запрещён; администратор сверяет кабинет и подтверждает восстановление.
- После перезапуска незавершённое `creating` становится `uncertain`, а `delivering` — `delivery_review`. Из этих состояний автоматической покупки/повторной отправки нет.
- Перед покупкой и выдачей заново проверяется заказ FunPay: статус PAID, продавец, покупатель, чат, описание, количество, отсутствие встроенной выдачи.
- Ошибки API отображаются без сырых тел ответа и ключа. Полученные коды хранятся локально и выдаются в чат покупателя после `completed`.

Гарантировать ровно одну доставку сообщения невозможно: FunPay может принять сообщение, а сетевой ответ потеряться. Поэтому в спорном случае требуется сверка чата. Аналогично проверка статуса FunPay и покупка у стороннего поставщика не являются общей транзакцией: возврат FunPay одновременно с запросом поставщику требует ручного разбора.

Плагин не определяет надёжность поставщика и не проверяет активацию каждого кода. Тесты подменяют сеть; покупки с реальным балансом не выполнялись.
